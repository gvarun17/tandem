Conventions used in this document

  • Must / Should / May follow RFC 2119: Must = required for MVP acceptance; Should = expected unless a reviewer approves otherwise; May = optional.
  • All timestamps are stored in UTC (timestamptz) and rendered in the household's IANA timezone. All money is stored as integer minor units (cents/paise) — never floats.
  • household_id appears on every tenant-owned table. Any query without it is a defect.
  • API examples are illustrative contracts; the generated OpenAPI 3.1 document is the normative source once the API skeleton is merged.

1. Design goals, principles & non-functional requirements

1.1 Goals

  1. One household, one source of truth. Two partners editing the same list, budget, or calendar must never create divergent copies.
  2. Isolation by construction. A bug in a query must not be able to leak another household's finance or health data — isolation is enforced in the database, not just in application code.
  3. Fast on a mid-range phone on 4G. The primary device is mobile; the web app is a Progressive Web App (PWA) first, native wrappers later.
  4. Boring, operable technology. A small team must be able to run this at 2 a.m.: managed services, one deployable API, full observability.
  5. Extensible without rewrites. Fitness (MVP-Lite) and home automation (Phase 3) plug into the same tenancy, events, and notification spine.

1.2 Principles

Modular monolith first
Modules (Tasks, Finance…) are packages with enforced boundaries inside one deployable. Extract a service only on measured need.
Server is authoritative
Clients keep an optimistic cache; the server owns conflict resolution, permissions, and all money maths.
Events for side effects
Domain events (transaction.created, stock.low) drive notifications, metrics, and automations — modules never call each other directly for side effects.
Privacy by default
Per-module visibility (shared / private), encryption at rest and in transit, data export and deletion as first-class features.

2. System architecture

2.1 Request flow (example: partner adds an expense)

  1. Client sends POST /v1/transactions with a JWT access token and an Idempotency-Key. CDN/WAF terminates TLS and applies per-IP rate limits.
  2. API auth middleware validates the token, loads membership, and sets the PostgreSQL session variable app.household_id for row-level security (RLS).
  3. Finance module validates the payload, writes the transaction and its splits in one DB transaction, and emits transaction.created to the internal event bus.
  4. Subscribers react asynchronously: budget-metrics cache is invalidated, the budget-alert rule is evaluated, and a WebSocket message is published via Redis to the partner's connected clients.
  5. Response returns 201 with the created resource and an ETag; the originating client reconciles its optimistic entry by client-generated ID.

2.2 Module boundaries

Modules communicate through typed in-process interfaces and domain events only — never by reading another module's tables directly. Cross-module reads (e.g., the dashboard) go through a read-model / view layer. Lint rules (dependency-cruiser or equivalent) fail CI on a boundary violation. This is what makes a later extraction — most likely candidate: the worker / integrations tier — a deployment change, not a rewrite.

3.1 What we deliberately do not use in MVP

  • Microservices / Kubernetes: operational cost with no MVP-scale benefit; containers on a managed orchestrator are enough. Revisit trigger in ADR-001.
  • GraphQL: REST + OpenAPI is simpler to cache, secure per-resource, and generate clients from. Revisit if client query diversity becomes painful.
  • A separate analytics database: finance metrics are PostgreSQL aggregations + materialised views until volume proves otherwise (Section 6.3).
  • Blockchain / local-first CRDT sync: server-authoritative sync with optimistic UI meets the freshness target with far less complexity.

4. Data model & database design

4.1 Tenancy and common rules

  • Every tenant table has id uuid PK, household_id uuid FK, created_at / updated_at timestamptz, created_by uuid, and deleted_at timestamptz NULL (soft delete; hard purge after 30 days).
  • RLS is enabled on every tenant table with policy household_id = current_setting('app.household_id')::uuid. The API connects as a non-owner role so RLS cannot be bypassed by accident.
  • Optimistic concurrency: mutable resources carry version int; updates require If-Match. Conflicts return 409 with the current resource.
  • Money: amount_minor bigint + currency char(3) (ISO 4217). Quantities: numeric(12,3). Dates that are household-local (birthdays, due dates) use date, never timestamps.

4. Data model (continued)

4.4 Finance schema — the integrity-critical part

accounts        id, household_id, name, type (cash|bank|card|wallet|loan),
                 currency, opening_balance_minor, archived
transactions    id, household_id, account_id, type (income|expense|transfer),
                 amount_minor (>0, sign from type), currency,
                 category_id NULL, merchant, note, occurred_at (date),
                 source (manual|import|recurring|rule), external_id NULL,
                 transfer_pair_id NULL, created_by, visibility
                 UNIQUE(household_id, account_id, external_id) WHERE external_id IS NOT NULL
transaction_splits  transaction_id, category_id, amount_minor, note
                 -- split amounts must sum to the transaction amount (DB trigger)
budgets         id, household_id, category_id NULL (= overall), period (monthly|custom),
                 amount_minor, rollover boolean, alert_thresholds int[] {50,80,100}
goals           id, household_id, name, target_minor, current_minor (derived),
                 target_date, account_id NULL, priority
recurring_schedules id, household_id, template jsonb, rrule, next_run_at, active
  • Balances are derived, never stored as truth: account balance = opening balance + signed sum of transactions. A materialised balance cache is maintained for list screens and reconciled nightly; any mismatch pages the on-call (it indicates a bug, not user error).
  • Transfers are two linked transactions (transfer_pair_id) created atomically; deleting one deletes both.
  • Imports are idempotent via the external_id unique constraint plus a fuzzy de-duplication pass (same account, amount, date ±2 days, similar merchant) flagged for user review — never silently merged.
  • Budget actuals are computed from transactions by category and period; budget_periods snapshots a closed month so historical reports never change when categories are renamed.

4.5 Indexing & performance rules

  • Composite index on every tenant table: (household_id, <primary access column>) — e.g., transactions(household_id, occurred_at DESC), tasks(household_id, due_at) where status is open.
  • Partial indexes for hot paths: open tasks, upcoming events (starts_at within window), low stock (quantity <= reorder_threshold).
  • Full-text search (groceries, merchants, tasks) via PostgreSQL tsvector + pg_trgm; no external search engine in MVP.
  • All list endpoints use cursor pagination (limit max 100); offset pagination is prohibited on tenant tables.
  • Slow-query log at 200 ms in staging; every migration ships with an EXPLAIN ANALYZE note for its main query.

4.6 Migrations, seeds & data lifecycle

Schema changes ship as versioned migrations (Prisma Migrate / Alembic equivalent), applied by CI before the new API version receives traffic; expand-migrate-contract for any destructive change. Seed data creates the default category taxonomy, units, and task lists used at household creation — the same seeds power demo mode. Retention: soft-deleted rows purged after 30 days; audit log retained 24 months; backups: daily snapshots + WAL PITR, 35-day retention, encrypted with a managed KMS key.

5. API design & contracts

5.1 Style rules

  • REST over HTTPS, JSON, versioned in the path: /v1/…. OpenAPI 3.1 is generated from the validation schemas and published in CI; breaking changes require /v2.
  • Auth: Authorization: Bearer <JWT> (15-min access token) + rotating refresh token (httpOnly, Secure cookie for web; secure storage on mobile). Every request resolves the active household from the membership claim or X-Household-Id header, validated against membership.
  • Errors use RFC 9457 Problem Details: {type, title, status, detail, code} with a stable machine code (e.g., budget_exceeded_warning, version_conflict).
  • Writes accept Idempotency-Key (UUID); keys are stored 24 h and replay returns the original response. Updates require If-Match: <version>.
  • Rate limits: 300 req/min per user (general), 30/min for imports and auth-adjacent endpoints, 10/min for invite sends. Limits return 429 with Retry-After.
  • Filtering: ?status=open&assignee=me&from=…&to=…; sorting allow-listed per resource; responses wrap lists as {data:[], next_cursor}.

5.4 Real-time API (WebSocket protocol)

  • Connect: wss://api…/v1/realtime with the access token in the first message (never in the URL, so it cannot leak into logs). Server replies ready with the connection's household subscriptions.
  • Messages: server → client: entity.changed (envelope in Section 8.1), presence.updated, ping. Client → server: subscribe, unsubscribe, pong. Clients never write data over the socket — all writes stay on REST, so validation, idempotency, and audit apply uniformly.
  • Ordering: events carry a per-household monotonic sequence; a gap triggers the resync flow (Section 8.1) rather than silent divergence.

5.5 Versioning, deprecation & client compatibility

  • Additive changes (new optional fields, new endpoints) ship inside /v1; the web client and API deploy together, and any future native app must tolerate one-version-old responses for 90 days after a breaking change is announced.
  • Deprecated fields are marked in OpenAPI, logged when consumed, and removed only in a new major version. Sunset responses carry Sunset and Deprecation headers.
  • File uploads never traverse the API: the client requests a pre-signed URL (POST /attachments:presign), uploads directly to object storage, then confirms; the API records metadata only after the AV scan passes.

6. Module designs

6.1 Tasks

  • Recurrence: RFC 5545 RRULE stored verbatim; a materialised next_due_at is maintained for querying. Completing a recurring task creates the next instance and a task_completions row (powers streaks/history). Editing a series follows the same this | following | all scope model as calendar events.
  • Ordering: fractional position values allow drag-reorder with a single-row update; rebalancing job runs when precision is exhausted.
  • Views are queries, not data: Today / This Week / Overdue / By Assignee are parameterised list queries over (household_id, due_at, status).
  • Reminders: on create/update, a delayed job is (re)scheduled in BullMQ at due_at − offset; job payload carries only IDs, state is re-read at fire time (a completed task never notifies).

6.2 Calendar

  • Storage: recurring events store one master row with RRULE + EXDATEs; occurrences are expanded server-side for the requested range (max window 13 months per query) — never materialised indefinitely.
  • Timezones: timed events store UTC instants + the event's original IANA timezone so DST transitions render correctly for travelling partners; all-day events store date ranges.
  • External sync: two-way sync with Google / Microsoft calendars via the adapter layer (Section 9). Sync uses provider change tokens/webhooks, maps external IDs in external_calendar_links, and resolves conflicts last-write-wins with the pre-conflict version kept in audit log and surfaced if both sides changed within 5 minutes.
  • Availability: free/busy is computed from expanded occurrences; no separate availability store.

6.3 Finance (metrics engine)

All PRD metrics are SQL aggregations over transactions, cached per household/period in Redis (TTL 15 min, invalidated on any transaction write in that household):

6. Module designs (continued)

6.4 Inventory & shopping

  • Stock adjustments are a ledger: every change writes a stock_movements row (delta, reason: purchase|use|waste|adjust, actor); stock_levels.quantity is the cached sum. This makes “where did it go?” answerable and undo trivial.
  • Low-stock rule: after any movement, if quantity <= reorder_threshold, emit stock.low → auto-add to the default shopping list (once, deduplicated by open shopping item) + optional notification.
  • Shopping check-off loop: checking a shopping item opens a quantity prompt (default: requested qty), writes a purchase movement, and — if the item is linked to a finance category — offers a one-tap expense pre-filled from the store/amount fields. The finance write only happens on explicit confirm.
  • Barcode: POST /items/scan looks up the household's own items first, then the cached products table, then the external product API (Section 9). Unknown barcodes create a stub the user names once; the result is cached for everyone (product catalogue data only — no household data is shared).
  • Expiry: expires_on date on stock batches where relevant; a daily job emits stock.expiring at 3 days and 0 days.
  • Home inventory valuation: purchase price + date on asset-class items; total insured-value report is a simple sum with a CSV/PDF export — no depreciation model in MVP.

6.5 Fitness (MVP-Lite)

  • Ingest: manual entries and device sync write metric_samples (steps, active_minutes, workouts, weight, sleep). Batch endpoint dedupes on (user_id, source, external_id); overlapping sources are priority-ordered (device > phone > manual) to avoid double-counted steps.
  • Privacy is per-user, not per-household: samples belong to a user; household aggregation only includes users whose module_visibility for fitness is shared. Challenges read aggregated totals, never raw samples of another user.
  • Goals & challenges: progress is a windowed sum over samples; challenge standings are computed on read for small groups (household-scale, no pre-aggregation needed). Streaks count days meeting the daily target in the user's own timezone.
  • Encouragement events: goal met / challenge lead change / partner PR emit fitness.milestone → notification with a one-tap reaction. No public feeds, no leaderboards beyond the household.

6.6 Dashboard & search

The home dashboard is a read-model endpoint (GET /dashboard) that fans out to module query services server-side and returns one payload with per-widget freshness timestamps, so a slow finance aggregation never blocks tasks. Global search queries each module's tsvector index with the same RLS context and merges ranked results; it never searches modules set to private by another member.

Consistency rule across modules: anything that moves money or stock is transactional and ledger-backed; anything that is a view (dashboard, reports, standings) is derived and rebuildable. If a derived number and its ledger disagree, the ledger wins and the derived value is recomputed.

6. Module designs — key flows

6.7 Sequence: recurring bill → reminder → payment recorded

  1. recurring_schedules.next_run_at is scanned by a minutely dispatcher job; due schedules create a draft transaction (status scheduled) and a task (“Pay electricity bill”) if the template requests one.
  2. Reminder jobs fire per the member's notification preferences; the bill appears in Cash-Flow Forecast (PRD 5.3) from the schedule, not from history.
  3. On the due date the draft becomes payable; one tap confirms it into a posted transaction (amount editable), which updates budgets and the forecast atomically.
  4. If unconfirmed after 3 days, a single escalation reminder is sent; the schedule's next occurrence is generated regardless, so a missed payment never blocks the series.

6.8 Sequence: household creation & partner invite

  1. POST /households creates the household, owner membership, default lists/calendars/categories from seeds, and a household.created audit entry — one DB transaction.
  2. Invite creates a hashed single-use token (raw token only in the emailed link), 7-day expiry. Accepting requires an authenticated account whose email matches the invite, or an explicit owner override.
  3. On accept, membership is activated, the new member gets default notification preferences, and a WebSocket member.joined event refreshes all clients.
  4. Leaving a household requires the leaver to export or abandon their private-module data; owners must transfer ownership first. Household deletion is owner-only, soft-deletes everything, and hard-purges after 30 days with a final confirmation email.

6.9 Offline & conflict behaviour (PWA)

CaseBehaviour
Reads offlineLast-synced cache (IndexedDB) served with a visible “offline / last synced” indicator

7. Authentication, security & privacy

7.1 Authentication & session design

  • OIDC/OAuth 2.1 via a managed identity provider: email+password (with breached-password screening), Google and Apple social login, and passkeys (WebAuthn) where the IdP supports them. The app never stores passwords.
  • Access token: JWT, 15 minutes, claims sub, household_ids (IDs only, no PII). Refresh token: opaque, rotating, reuse detection revokes the whole token family.
  • MFA: TOTP/push MFA available to all, required to view connected-account balances, export finance data, or delete a household.
  • Sessions screen lists devices with last-active time; “sign out everywhere” revokes all refresh families and WebSocket connections.

7.2 Authorisation model

LayerMechanism
Tenant isolationPostgreSQL RLS on household_id (defence layer 1)
MembershipAPI middleware: user must hold an active membership in the requested household (layer 2)
RoleOwner/Admin/Member/Child/Guest capability matrix (PRD 5.7) enforced per endpoint (layer 3)
Module privacymodule_visibility check for private finance/fitness data (layer 4)

Authorisation tests are written as a matrix: every endpoint × every role × own/other household, run in CI. A new endpoint without matrix tests fails review.

7.3 Data protection

  • In transit: TLS 1.2+ everywhere, HSTS, secure cookies, certificate pinning in any future native wrapper.
  • At rest: managed-disk/KMS encryption for DB, Redis, and object storage; field-level encryption (envelope, per-household key) for bank external IDs and any future health identifiers.
  • Secrets: in a managed secret store, injected at runtime; never in code, images, or logs. Log scrubbing for tokens, amounts in URLs, and email bodies.
  • Uploads: pre-signed S3 uploads, AV scan before scan_status=clean, images re-encoded server-side (strips EXIF location by default).
  • AppSec: parameterised queries only, output encoding, CSP, CORS allow-list, dependency scanning (Dependabot/Renovate), SAST + DAST in CI, OWASP ASVS L2 checklist per release.

7.4 Privacy & compliance posture

  • Data export (JSON + CSV, per PRD NFR) generated asynchronously, delivered via a 48-hour signed link, and audit-logged. Account deletion anonymises audit rows and hard-deletes content within 30 days.
  • Fitness/health data is treated as sensitive: explicit consent on first sync, per-user visibility defaulting to shared-with-household only after opt-in, and never used for advertising or sold — stated in the privacy policy.
  • Bank aggregation (when enabled) uses a regulated aggregator; Tandem stores tokens and transactions, never bank credentials. Design anticipates GDPR/CCPA-style rights (access, rectification, erasure, portability) regardless of launch market.
  • Children's accounts (if enabled) are view/task-limited, cannot see finance detail, and require an owner to create them.

8. Real-time sync, notifications & background jobs

8.1 Real-time sync

  • WebSocket endpoint GET /v1/realtime (Socket.IO or native WS with a thin protocol). Clients subscribe per household after auth; the server joins them to a Redis pub/sub channel household:{id}.
  • Event envelope: {event_id, type, household_id, entity, entity_id, version, actor_id, at}. Payloads carry IDs and versions, not full records — clients refetch (or patch from the REST response they already have), which keeps sync consistent with permissions and visibility.
  • Heartbeat every 25 s; automatic reconnect with backoff; on reconnect the client sends last-seen event_id and receives a “resync required” flag if the gap exceeds the in-memory buffer, triggering a normal REST refresh.
  • Presence (who is online / viewing a list) is ephemeral in Redis with 60 s TTL — never persisted.

8.2 Notification service

9. Integrations & future home automation

9.1 Integration architecture

Every external system sits behind an adapter interface owned by Tandem (ports-and-adapters). Adapters translate provider payloads into Tandem domain objects, store the raw payload (encrypted, 90 days) for reprocessing, respect provider rate limits with token-bucket throttling, and surface a per-connection health status to the user (“Bank sync delayed”). No module code imports a provider SDK directly.

IntegrationInterface / provider patternMVP stance
Bank / card aggregationAccountAggregator — Plaid (US) / equivalent regional provider; webhooks → imports queuePhase 2; CSV import is the MVP path. Schema already carries external_id
CalendarsCalendarSync — Google Calendar API, Microsoft Graph; change tokens + push channelsPhase 2 (one provider first, Google)
Barcode / product dataProductCatalogue — Open Food Facts-style API + local cacheMVP: lookup + cache; graceful manual fallback
FitnessHealthSource — Apple HealthKit & Health Connect (via mobile wrapper), Fitbit/Garmin web APIsMVP-Lite: manual + one device path; web APIs in Phase 2
Files / receipts OCRDocumentText — managed OCR (e.g., Textract) behind interfacePhase 2: receipt total/merchant extraction into a draft expense

9.2 Home automation — extension design (Phase 3, reserved now)

  • New module, same spine: devices, device_states, automations, scenes tables with household_id; device commands flow through the existing event bus and audit log, so “who opened the garage at 23:14” is answerable from day one of the feature.
  • Local-first control: a household hub/gateway (or the mobile app on the home network) speaks Matter/Thread and HomeKit locally; the cloud relays commands only when remote, and automations that are safety-relevant (locks, garage) must be executable locally if the internet is down.
  • Safety gates by design: actuation endpoints require step-up authentication for locks/garage doors, enforce per-device capability allow-lists, rate-limit commands, and default to notify-both-partners for security devices. Read-only telemetry (temperature, energy) ships before any actuation.
  • Vendor neutrality: DeviceProvider adapters (Matter, HomeKit, vendor clouds such as SmartThings) map to a common capability model (on_off, dim, lock, open_close, temperature) — Tandem never models a brand's proprietary object tree.
  • Why this is only a reservation in MVP: no device tables ship in MVP migrations; what ships is the event bus, audit log, and module pattern that make the addition incremental rather than architectural.

10.2 Observability & operations

  • Signals: OpenTelemetry traces (API → DB → queue), RED metrics per endpoint, structured JSON logs with correlation_id, household_id (hashed), user_id; finance payloads and health samples are never logged.

Appendix A — Environments, naming & glossary

Naming: tables are plural snake_case; API resources are plural kebab-case; events are entity.action past-tense nouns (e.g., transaction.created); queues are lowercase nouns. Glossary: Household — the tenant unit (a couple or family). Member — a user belonging to a household. Ledger — an append-only record (stock movements, audit) from which current state is derived. Outbox — the pattern of writing an event row in the same transaction as the data change, relayed asynchronously. RLS — PostgreSQL row-level security. RRULE — the iCalendar recurrence rule format (RFC 5545). Open questions for review: (1) NestJS vs Fastify — decide in Phase 0 by team preference; contracts here are unaffected. (2) Launch currency/region for payments law and aggregator choice. (3) Native wrapper timing — PWA-only at launch is assumed; revisit if HealthKit depth is required for Fitness GA.
