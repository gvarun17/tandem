1. The problem: a household runs on scattered apps and memory

A couple already runs a small organisation - chores, bills, appointments, groceries, savings goals, and the house itself. Today that work is split across a notes app, a chat thread, a personal calendar, a banking app neither partner fully sees, and memory. The result is predictable: duplicated purchases, missed renewals, "I thought you were paying that," and long-term goals that never get a weekly action attached to them.

Vision. Tandem is the household's single shared operating system: one place where both partners see the same tasks, the same calendar, the same money picture, and the same state of the home - and where every long-term goal breaks down into this week's tasks, budget, and calendar time.

Who it is for

  • Primary: a married or cohabiting couple sharing expenses, a home, and a calendar, on mixed devices.
  • Secondary: the wider family in the same home - parents, older children - with narrower, role-based access.
  • Not for (MVP): roommates splitting rent only, landlords, or multi-household property management.

Product principles

  1. Shared by default, private by choice. Household items are visible to both partners; any item can be marked personal.
  2. Capture in under 10 seconds. Adding a task, expense, or grocery item must be faster than sending a chat message about it.
  3. Show the household, not just the person. Every dashboard answers "how are we doing?" before "how am I doing?"
  4. No blame design. Finance and fitness views compare against the plan, never partner against partner as a league table by default.
  5. Calm notifications. Digest-first; interrupt only for time-critical items the user opted into.

Jobs to be done

When...The couple wants to...
Planning the weekSee tasks, events, and money due in one view
Something needs doingAssign it, set a due date, and trust it will not be forgotten
Money comes in / goes outKnow what is safe to spend and whether savings are on track
Shopping or cookingKnow what is already at home before buying more
Reviewing the monthSee progress on goals without building a spreadsheet
Life gets busyGet a gentle nudge, not another noisy feed

Personas (summary)

The Organiser - plans ahead, keeps lists, wants structure and a weekly review. The Doer - acts on clear, short lists; will not maintain a complex system. The product must satisfy the Organiser's depth while never punishing the Doer: sensible defaults, one-tap completion, and no mandatory fields beyond a title and a date where relevant.

Differentiation in one line: Existing apps do one slice well (to-do, budgeting, or grocery lists). Tandem's value is the joins between them - a goal creates budget + tasks + calendar time; a low-stock grocery creates a shopping task; a bill is both a calendar event and a finance forecast.

3. Tasks and Calendar: the household's week, in one view

Module A - Tasks (daily, weekly, recurring)

Tasks are the atomic unit of household work. Every task has a title, an owner (one partner, both, or unassigned), a due date/time, a list, and a visibility (shared or personal). Everything else is optional, so capture stays fast.

RequirementDetail and rules
Create / edit / completeQuick-add from any screen (keyboard shortcut + floating button). Complete with one tap; completed tasks stay visible struck-through until end of day, then move to history.
ViewsToday (due today + overdue), This Week (grouped by day), Lists (custom lists, e.g. Home, Kids, Admin), Mine / Partner's / All filter. Default home view is Today + This Week combined.
RecurrenceDaily, weekly, monthly, custom interval, and "after completion" recurrence (next occurrence created only when the current one is done - for chores like changing filters). Support rotating assignee for shared chores.
Assignment + nudgesAssigning a task notifies the assignee once. One gentle reminder before due time; overdue tasks roll into Today with an overdue marker - never silently deleted.
Subtasks + notesUp to 10 subtasks, free-text notes, optional link to a calendar event, a budget category, an inventory item, or a goal.
Acceptance criteriaA task created by Partner A appears for Partner B within 5 seconds on a normal connection; recurring series can be edited for "this event only" or "this and following"; deleting a series requires confirmation.

Module B - Calendar

RequirementDetail and rules
CalendarsOne Household calendar (both partners), plus a Personal calendar per user visible only to them. Events can be household or personal; personal events can optionally show as "Busy" (time blocked, no details) to the partner.
EventsTitle, start/end, all-day, location, notes, attendees (household members + free-text guests), reminders (multiple), recurrence with exceptions, colour by calendar/category.
ViewsMonth, Week, Day, and Agenda. Agenda is the default on mobile. Tasks with due times appear on the calendar as toggleable overlay items - not as events - so the week reads as one plan.
Joins with other modulesBills appear as forecast markers on their due dates; birthdays/anniversaries are first-class recurring events with gift-task prompts (optional); fitness sessions and goal milestones can be placed as events.
External syncMVP: one-way import/subscribe (ICS) + export. Phase 1.5: two-way sync with Google Calendar and Apple Calendar, with a clear conflict rule (last edit wins, conflict shown, never silently overwritten).
Acceptance criteriaCreating an event with a reminder fires that reminder within 1 minute of schedule across web push/email per user settings; timezone is stored per event and displayed correctly when a partner travels.
Design rule: One combined "Week" screen - calendar on top, tasks beneath each day - is the signature view. If a feature does not make it more useful, it is not MVP.

4. Finance: one money picture both partners trust

Finance is a tracking and planning tool in MVP - it records and explains money, it does not move money. Manual entry must be excellent first; bank import (CSV in MVP, aggregation later) reduces the burden without becoming a dependency.

Core objects

ObjectFields and rules
AccountsName, type (current/checking, savings, credit card, cash, loan, investment - tracking only), owner (joint / Partner A / Partner B), currency, opening + current balance, optional credit limit and statement/due dates for cards.
TransactionsAmount, date, payee/description, category, account, entered-by, type (income, expense, transfer), split flag (shared / personal / split %), receipt photo (1.5), note. Transfers between own accounts never count as income or expense.
CategoriesStarter set (Groceries, Dining, Utilities, Rent/Mortgage, Transport, Health, Home, Fun, Kids, Other) - fully editable, with subcategories. Every transaction has exactly one category.
BudgetsPer category, per month (weekly view derived). Set as a household amount; optional per-partner personal budgets for personal categories. Rollover on/off per budget.
Bills + recurringRecurring income/expenses with frequency, next due date, account, and auto-create toggle. Bills feed the calendar and the cash-flow forecast.
Savings goalsName, target amount, target date, linked account(s), contributions (manual or auto-scheduled as recurring transfers), priority. Progress shown as amount + % + required monthly pace.
SettlementsFor split expenses, a running "who owes whom" balance with a one-tap "mark settled" - the app records the settlement; payment itself happens outside the app in MVP.

Entry experience - the make-or-break detail

  • Add expense in 3 fields or fewer: amount, category (suggested from history), account (defaults to last used). Date defaults to today; partner attribution defaults to shared.
  • Quick-add from the home screen and from the Inventory shopping list (a bought item can become an expense in one tap).
  • Duplicate detection on import and on rapid re-entry; every import is previewed and reversible as a batch.
  • Both partners see new transactions in near-real time, with "added by" attribution - transparency without surveillance framing.
Trust rule: Either partner can edit a shared transaction, but edits are kept in an activity history (who changed what, when). Nothing in finance is silently overwritten - that history is what makes a shared money tool feel safe.

5. Finance metrics: the dashboard that answers "how are we doing?"

The money home screen shows a small, stable set of metrics - the same ones every week, so the couple learns to read them at a glance. Definitions below are normative: the TDD implements exactly these formulas.

MetricDefinitionWhy it matters
Net positionSum of all account balances minus loans/credit-card balances owed. Shown as one number + 6-month trend.The household's headline health number.
Safe to spendLiquid balances - bills due before next payday - budget amounts reserved for the rest of the month.Answers "can we afford this?" without mental maths.
Income vs. spendingTotal income and total expenses this month (transfers excluded), with the same period last month alongside.Direction of travel, not just a snapshot.
Savings rate(Income - expenses) / income for the month, as a %. Also shown as a 3-month average to smooth noise.The single habit metric most linked to long-term goals.
Budget healthPer budget: spent, remaining, and pace status (on pace / watch / over) based on day-of-month vs. spend proportion.Early warning, while there is still time to adjust.
Cash-flow forecastProjected balance for the next 30/60/90 days from scheduled bills, recurring income, and average discretionary spend.Prevents the "big bill in a quiet month" surprise.
Bills due (7 / 30 days)List + total of bills due in the window, with the account each will draw from.Pairs with the calendar forecast markers.
Savings goal pacePer goal: saved, % of target, months remaining, required monthly amount vs. actual average contribution.Turns a wish into a monthly number.
Category breakdownSpend by category this month (bar/donut), tap to drill into transactions; top-3 movers vs. last month called out in words.Shows where money actually went, in plain language.
Settlement balanceNet amount one partner owes the other from split expenses, with history.Keeps shared costs fair without a side spreadsheet.
Fixed vs. flexibleRecurring/fixed spend as a share of income vs. discretionary spend share.Shows how much room the household really has to adjust.

Reporting and review

  • Weekly digest (in-app + email/push, opt-in): spent this week, budgets at risk, bills next week, one savings-goal update, tasks completed. One screen, no shaming language.
  • Monthly review screen: income vs. spending, savings rate, category movers, goals progress, and a prompt to adjust next month's budgets - designed as a 10-minute together ritual.
  • Export: transactions and budgets exportable as CSV at any time. The household's data is theirs; export is a feature, not a support ticket.

Currency: One primary household currency in MVP, with per-account currency stored and converted at a stored rate for display totals (rate source and date shown). Full multi-currency budgeting is Phase 2.

6. Inventory: what is in the house, and what is about to run out

Inventory has two halves with different rhythms. Groceries move fast - quantities change weekly and the payoff is a shopping list that builds itself. Home inventory moves slowly - appliances, furniture, documents, warranties - and pays off when something breaks, gets insured, or needs replacing.

Groceries and consumables

RequirementDetail
ItemName, quantity + unit, location (pantry/fridge/freezer/bathroom), category, low-stock threshold, expiry date (optional), barcode (optional, Phase 1.5 scan)
Stock actionsAdd, use up (-1 / set quantity), restock. One-tap +/- on the item row; full edit only when needed.
Low-stock ruleWhen quantity is at or below threshold, the item appears on the Shopping List automatically (once - no duplicates).
Expiry view"Use soon" list sorted by expiry; optional digest mention. No alarm-style notifications by default.
Shopping ListAuto items + manually added items, grouped by store/aisle category, check-off in store, quantity, assigned shopper. Checking off in "shopping mode" restocks inventory and can create a finance expense in one tap.
StaplesMark an item a staple to keep it permanently threshold-tracked (milk, rice, detergent) vs. one-off items that disappear when used up.

Home inventory (everything else)

RequirementDetail
ItemName, room/location, category, purchase date + price, serial number, warranty expiry, photo(s), receipt/document attach, notes (e.g. filter size, paint colour)
RoomsKitchen, Living, Bedroom, Bathroom, Garage, Storage + custom rooms. Browse by room or search globally.
RemindersWarranty expiring, maintenance due (recurring task auto-created, e.g. HVAC filter), insurance review - all surface as tasks/calendar items, not a separate inbox.
Value viewTotal recorded value by room/category - useful for insurance. Exportable as PDF/CSV list.
Loaned / storedStatus flag: in use, stored, loaned out (to whom), disposed/sold - so the list stays truthful over years.

Acceptance criteria (both halves)

  • Searching "batteries" finds the item, its room, and its quantity in under 2 seconds of typing.
  • Buying a shopping-list item updates stock, removes it from the list, and (if chosen) logs the expense - in a single flow.
  • Inventory is fully usable offline for viewing and stock changes, syncing on reconnect (see TDD sync rules).
Scope discipline: MVP inventory is a trusted list, not a smart-kitchen platform. No recipe engine, no automatic ordering, and no image recognition in v1.0 - those are Phase 2 candidates only if beta households ask for them unprompted.

7. Fitness, goals, and the layer that joins everything

Module E - Fitness (Phase 1.5 - designed now, built after MVP)

Fitness is specified here so the data model and home screen reserve space for it, but it does not block the MVP launch. Its tone is the product in miniature: encouragement, never comparison-as-competition by default.

RequirementDetail
Metrics trackedWorkouts (type, duration, date, who), steps, weight (personal by default, shareable by choice), sleep (manual or wearable-imported where available). Manual entry is the baseline; device import is an enhancement, never a requirement.
Shared goalsHousehold or paired goals, e.g. "3 workouts each this week", "walk together twice a week", "10k steps/day streak - combined". Progress is shown as joint progress first, individual contribution second.
EncouragementOne-tap kudos on a partner's completed workout or hit goal; streaks celebrated in the weekly digest. No public ranking, no weight league tables, no negative streak-shaming.
Scheduling joinFitness goals can generate calendar blocks and recurring tasks ("Tue/Thu 7am workout"), so intent becomes time, not just a chart.
PrivacyWeight and health notes are personal by default. A partner sees only what the other explicitly shares. This default is not changeable by the other partner.

The Goals layer (spans all modules)

Long-term goals are what separate Tandem from a bundle of utilities. A Goal (e.g. "Save for a house deposit", "Get fit by June", "Renovate the kitchen") has a target, a date, an owner pair, and linked objects: a savings goal in Finance, milestones as Calendar events, and next actions as Tasks. The Goal screen shows one progress view assembled from those links - no duplicate data entry.

  • MVP: goals exist as lightweight objects linking one savings goal + any tasks/events, with a manual progress note.
  • Phase 1.5: milestones, fitness-goal links, and a quarterly review prompt.

Cross-cutting requirements

AreaRequirement
Household + rolesHousehold is the tenant. Roles: Partner (full), Member (family - configurable modules), Child/Guest (view + own tasks only, no finance by default). Invite by link/email; leaving a household exports the leaver's personal items and removes shared access immediately.
Home screenToday strip: today's events + tasks, safe-to-spend, bills this week, low-stock count, and one goal highlight - in that priority order, each tappable to its module.
NotificationsPer-user controls by type (task assigned/due, event reminder, bill due, budget alert, digest). Channels: web push + email in MVP. Defaults are quiet; budget alerts fire only at 80% and 100% of a budget.
SearchOne search box across tasks, events, transactions, inventory, and goals, with type filters. Results respect visibility - personal items never appear in a partner's search.
Activity feedHousehold activity (added/completed/edited) in one chronological feed, filterable by module. In finance this doubles as the audit history.

8. Experience, quality bar, risks, and launch gates

User experience requirements

  • Onboarding in under 5 minutes: create account, create/join household, invite partner, pick 3 starter lists/budgets from templates, done. Full setup can be deferred without penalty.
  • Empty states teach: every empty module shows one example action ("Add your first bill") - never a blank screen or a tutorial video gate.
  • Mobile-first: all MVP flows completable one-handed on a phone-sized screen; desktop adds density (week grid, finance tables), not exclusive features.
  • Accessibility: WCAG 2.1 AA target - sufficient contrast, full keyboard operation, visible focus, screen-reader labels on icon actions, no meaning carried by colour alone (budget pace also uses words).
  • Language: Plain, warm, non-judgmental copy. Dates, numbers, and currency always formatted to the household's locale.

Non-functional requirements

AreaBar for MVP
PerformanceHome screen interactive in under 2.5s on a mid-range phone / 4G; list screens paginate or virtualise beyond 100 items.
ReliabilityNo data loss on refresh, crash, or offline edit; offline queue for tasks/inventory/transactions with visible sync state.
PrivacyHousehold data visible only to its members; personal items visible only to their owner; encryption in transit and at rest; full data export and account deletion self-serve.
Availability99.5% monthly target for a small-team SaaS; status communicated in-app during incidents, never silent failure.

Top risks and mitigations

RiskMitigation
Second-partner drop-off (one partner uses it, the other does not)Design for the Doer (p.2); activation metric tracks both partners; digest gives the lighter user value without data entry.
Finance data-entry fatigue3-field entry, history-based suggestions, CSV import in MVP, recurring bills auto-created.
Scope creep toward "everything app"Phase gates in Section 2 are contractual; new modules need a phase decision, not a feature request.
Trust incident (wrong visibility)Visibility tests are release-blocking (see TDD); activity history on all shared finance edits.
Health-data sensitivity (1.5)Personal-by-default, explicit sharing, no advertising use - ever.

Launch gates (all must pass for public v1.0)

  1. Both-partner flows (invite, shared task, shared expense, shared event) pass end-to-end tests on phone and desktop browsers.
  2. Visibility/privacy test suite passes with zero failures - a personal item leaking to a partner is a launch blocker, not a bug to triage later.
  3. Finance metric definitions on page 6 verified against a worked test dataset by hand.
  4. Export + account deletion work end-to-end and are reachable in 3 clicks from Settings.
  5. Private beta (10-20 households, 4 weeks) with no data-loss incidents and activation at or near target.

Open decisions for the PRD (owner: product)

  • Domain and visual identity for Tandem (product name confirmed); trademark check to complete before public launch.
  • Free vs. paid shape (recommendation: free for one household's core; paid tier later for automation/integrations - decide before public launch, not before beta).
  • First launch locale/currency defaults and date conventions.

9. Architecture: a modular monolith that can grow up later

For a small team, the fastest safe architecture is a modular monolith - one deployable web application with strict module boundaries (household, tasks, calendar, finance, inventory, goals, notifications) - backed by one relational database. It gives real-time sharing and transactional finance correctness without microservice overhead, and each module can be extracted later if scale ever demands it.

10. Data model: household tenancy is the core invariant

Every domain row carries household_id. Every query is scoped by it, enforced in a single data-access layer and verified by tests - tenancy is never left to individual route handlers to remember. Money is stored as integer minor units (cents/paise) with a currency code; timestamps are UTC with the event's original timezone stored alongside where it matters.

Invariants the database + service layer must enforce

  • A transaction's account and category must belong to the same household as the transaction.
  • Balances are derived or transactionally maintained - never edited directly by a client; balance corrections are themselves transactions.
  • Deleting a household soft-deletes first (30-day recovery), then hard-deletes including object storage - tested end-to-end.
  • Personal-visibility rows are filtered in the data layer by owner = current user, in addition to household scoping.

11. APIs, realtime, and the jobs that run the household clock

API shape

REST over the Next.js Route Handlers under /api/v1/, JSON in/out, validated with a schema validator (e.g. Zod) sharing types with the frontend. Every list endpoint supports cursor pagination; every write returns the full updated entity so the client never guesses state.

POST   /api/v1/households            create household
POST   /api/v1/households/:id/invite invite partner/member
GET    /api/v1/tasks?view=today      today / week / list views
POST   /api/v1/tasks                 create (idempotency-key supported)
PATCH  /api/v1/tasks/:id             edit incl. recurrence scope
GET    /api/v1/events?from&to        range query for calendar views
POST   /api/v1/transactions          add income/expense/transfer
GET    /api/v1/finance/dashboard     all page-6 metrics, one call
POST   /api/v1/transactions/import   CSV import (preview -> commit)
GET    /api/v1/inventory?kind=grocery
POST   /api/v1/shopping-list/:id/check  restock + optional expense
GET    /api/v1/search?q=             cross-module, visibility-filtered
GET    /api/v1/export                full household/personal export (CSV/ZIP)

Realtime sharing

  • When Partner A creates/completes a shared item, Partner B's open app reflects it within ~5 seconds (PRD acceptance). Implementation: server-sent events or a lightweight websocket channel per household, with polling fallback; payloads carry entity id + version, clients refetch the entity - no complex CRDT needed at household scale (2-6 users).
  • Conflict rule: last-write-wins per field group with optimistic locking (version column); a stale write returns 409 and the client shows "updated by your partner - review" rather than overwriting.
  • Offline: capture flows (task, expense, stock change) queue locally with client-generated ids and idempotency keys; sync replays in order and surfaces (never hides) any conflict.

12. Security, privacy, testing, and operations

Authentication and authorisation

  • Passwords hashed with a modern adaptive hash (argon2/bcrypt); magic-link and Google OAuth as alternatives; sessions are httpOnly, secure, same-site cookies with refresh rotation.
  • Authorisation check order on every request: authenticated user, then household membership, then role, then row visibility (shared vs. personal, finance access for guest/child roles).
  • Rate limits on auth, invite, import, and export endpoints; invite links are single-household, expiring, and revocable.
  • Step-up confirmation (re-enter password / confirm) for: household deletion, member removal, and full data export download.

Privacy by construction

  • No advertising SDKs, no sale or sharing of household data, analytics events carry ids and counts - never amounts, item names, or health values.
  • Logs redact amounts, emails, and free-text fields; error reports strip payloads by default.
  • Encryption in transit (TLS everywhere) and at rest (managed DB + encrypted object storage); signed, short-lived URLs for every file.
  • Self-serve export and deletion (PRD launch gate), with deletion covering DB rows, files, push subscriptions, and analytics identifiers.

Testing strategy (release-blocking items marked *)

DevOps and environments

  • Environments: local, staging (seeded demo household), production. CI runs lint, types, unit + API tests, and migration checks on every PR; merges to main auto-deploy to staging.
  • Database migrations are forward-only in production with a tested rollback plan per release; daily automated backups with a rehearsed restore (test restore monthly).
  • Feature flags for Phase 1.5+ modules (fitness, sync) so code can ship dark; kill switch for push/email sending.
  • Monitoring: uptime, API latency/error dashboards, job-success alerts, and a privacy-safe product funnel (signup, invite accepted, first shared action).
The one rule above all others: a cross-household or partner-visibility leak is a severity-1 incident - stop, fix, audit the activity log, and disclose to affected households. Every other bug queues behind that principle.

14. Decisions, risks, and what to do next

Key architecture decisions (ADR summary)

  • ADR-01 Hosting pair - choose app host + managed Postgres at kickoff; optimise for boring reliability over novelty.
  • ADR-02 Monolith first - extract a service only on measured pain (first candidate: the jobs/realtime worker, then the Phase-3 device service).
  • ADR-03 Money as integers - minor units + currency code everywhere; floating point never touches money.
  • ADR-04 RRULE for recurrence - store the standard rule string, materialise occurrences in jobs; do not invent a custom recurrence format.
